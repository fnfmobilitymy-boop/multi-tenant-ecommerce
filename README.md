# EZShop

为马来西亚商家打造的多商家商店、订单及代理佣金应用。由原有 Python 原型逐步迁移，保留了商家后台功能，新增 React 19 + TypeScript + Tailwind CSS 4 顾客端。

**当前状态：可运行、可测试的开发版本，不是完整已上线的商业 SaaS。已增加 Stripe Connect 收款和平台订阅代码，尚未配置/部署或验证真实交易；自动银行转账未实现。邮件投递、生产备份及远端验收需外部服务和管理权限。详见 [上线配置与阶段验收](docs/上线配置.md)。**

## 当前可以做什么

- 商家注册/登录、独立商店链接、商品新增/编辑/发布/下架、分类、描述和图片上传。
- 商家订单管理、商品成交快照、手动确认实际收款、取消未付款订单并原子恢复库存，以及已完成线下全额退款的登记。
- 商家专属代理链接、订单归属、佣金统计；仅已确认付款的订单计入收入。
- 代理独立登录与专属工作台，只能查看自己的订单业绩，不暴露顾客邮箱和地址。
- 团队邮箱邀请（7 天有效、一次性接受）、订单客服/库存专员/经理分工、服务端权限控制、撤销会话及操作记录。
- 平台管理员可查看商家、分配 Free/Pro 标识和暂停/恢复店铺；管理员只能由可信数据库操作授权，注册请求不能自行升级。
- 确认收款后自动加入收据队列，提供 24 小时未付款提醒排队任务、幂等邮件发送任务与通知记录；不会将排队状态冒充已发送。
- 顾客首页、分类搜索、商品详情、相关推荐、按店铺隔离并持久化的购物车、独立结账与安全订单结果页。
- 后端重新计算金额及校验库存；支持幂等请求、跨商家校验、商品编辑库存冲突保护。
- 支持商家 Logo/Banner 直接选图上传及热门商品设置。商品图片未配置时使用明确的图标占位；规格说明保存在数据库并写入订单快照；不同规格分别创建独立商品管理价格及库存，复杂规格组合尚未实现。
- 邮费由商家自行填写，按每单固定金额计算，填 0 为免邮；折扣功能未开放。默认使用「联系商家付款」；配置并完成 Stripe Connect 认证后才显示线上付款入口，无虚假支付成功。

## 本地运行

需要 Node.js 22.12+（建议 24）和 Python 3.12+。

```sh
npm ci
npm run build
npm run server
```

服务默认绑定本机 3000 端口，提供构建后的 React 页面及 API。开发时另开终端执行 `npm run dev`，Vite 将 API 代理到 3000。`PORT` 和 `EZSHOP_DB` 可更改本地 API 端口和 SQLite 文件位置。没有默认账户；通过页面注册。

`server/data/`、环境变量文件和真实业务数据不会提交到 GitHub。原版后台页面保留在 `server/legacy.html`，本地服务 `/legacy` 可用于迁移对照。

## 顾客端路由

- `/shop/:slug`
- `/shop/:slug/product/:productId`
- `/shop/:slug/cart`
- `/shop/:slug/checkout`
- `/shop/:slug/order-result?ref=...`

订单结果查询需要独立高熵凭证，凭证保存在当前浏览器标签页的 sessionStorage，刷新仍可使用，不出现在 URL 中。其他浏览器仅凭订单号无法访问。当前未实现邮件找回访问链接，因此请勿把当前结果页当作完整的顾客账户系统。

## Supabase 模式

没有配置时使用经过集成验证的本地 Python/SQLite API。设置以下公开项目配置后，前端会切换到 Supabase Auth 和 `ezshop_api` RPC：

```text
VITE_SUPABASE_URL=https://你的项目.supabase.co
VITE_SUPABASE_ANON_KEY=项目 anon 或 publishable key
```

**绝不可在 VITE\_ 变量里放 service_role、数据库密码或支付密钥。**

`supabase/migrations/` 中按编号排序的迁移提供隔离的 `ezshop` schema、RLS、受控 RPC、库存事务和订单访问凭证处理。已通过本地 PostgreSQL（PGlite）执行与权限测试，但**没有连接实际 Supabase 项目执行**，也没有验证远端 Auth、邮件或并发连接行为。已有项目须先检查现有表和迁移，不能盲目重复建模。新项目可审查后在 Supabase SQL Editor 依次应用迁移；已应用初版的项目只应用新增的 002 迁移，不重新运行初版。须在 Supabase Auth 配置实际站点地址及邮件确认策略。

本地 SQLite 数据不会自动复制到 Supabase，正式使用前需单独迁移与核对。

## GitHub Actions

**EZShop · 构建与测试**：推送 main、PR 或手动运行。执行 TypeScript 构建、购物车/PostgreSQL 测试、本地 API 测试和 Chromium 完整业务流程，上传构建及截图。

**EZShop · 手动发布网站**：不随 push 自动发布。只有用户手动运行并输入 `DEPLOY` 才发布 GitHub Pages。先完成：

1. 配置真实 Supabase 项目，并审查、应用及验证迁移。
2. 在 GitHub 仓库 Settings → Secrets and variables → Actions → Variables 添加 `VITE_SUPABASE_URL` 和 `VITE_SUPABASE_ANON_KEY`（公开项目配置）。
3. 在 Settings → Pages 将 Source 设为 GitHub Actions。
4. 在 Actions 运行手动发布工作流。网址以成功运行的 `github-pages` deployment 输出为准。

GitHub Pages 只托管静态前端，不运行 Python。缺少 Supabase 配置时发布工作流会失败并提示配置，不会发布一个假装可用的网站。Pages 的深链接回退使用 404.html，直接刷新深路径时可能返回 HTTP 404 状态；正式商用推荐支持 SPA 重写与自定义域名的托管服务。

## 团队、代理与平台管理员

商家后台「团队与权限」创建指定邮箱的邀请，将生成的安全链接交给对应成员。链接 7 天内有效，只能领取一次。代理在自己的账号登录后进入专属门户；库存专员只能管理商品，订单客服只能处理订单，经理可以处理商品及订单。团队成员不能管理店铺设置、邀请成员或访问平台管理。撤销权限后，现有会话的后续请求也会被拒绝。

本地平台管理员先通过 UI 注册，再在可信终端执行：

```sh
python3 server/manage.py grant-admin 商家注册邮箱
# 撤销：python3 server/manage.py revoke-admin 商家注册邮箱
```

Supabase 模式由项目管理员在 SQL Editor 中将受信任账号的 `ezshop.merchants.is_admin` 设置为 true。不要将此授权开放为浏览器可调用的自助接口。没有预置管理员或默认密码。

## 自动收据及付款提醒

邮件队列的 `sent` 表示邮件服务商已接受请求，不保证最终投递。重复确认收款不会重复产生收据；发送任务使用稳定幂等键，失败最多重试 3 次。已取消或已付款的订单不再发送待付款提醒。

本地：配置服务端 `RESEND_API_KEY`、经 Resend 验证的 `MAIL_FROM`，由用户的定时调度器运行：

```sh
python3 server/notifications.py enqueue-reminders
python3 server/notifications.py dispatch
```

不配置时不会发送。测试使用本地模拟服务商，没有给真实客户发邮件。

Supabase：代码位于 `supabase/functions/send-notifications/`。在项目安全配置设置 `RESEND_API_KEY`、`MAIL_FROM` 和高熵 `NOTIFICATION_JOB_SECRET` 后，审查并部署函数，再配置定时 POST 请求，Authorization 为 `Bearer <NOTIFICATION_JOB_SECRET>`。函数使用 Supabase 自带的服务端服务角色；密钥不得进入前端或 Actions 公开变量。函数和定时任务当前未部署，Resend 实际投递未经远端验证。

## 佣金结算与全额退款登记

代理门户可以提交提现申请。金额按整数 sen 保存，提交后预留可用佣金；重复请求不会重复预留，同一请求标识不能换成不同金额。商家所有者在「佣金结算」查看申请及代理提供的收款资料，实际通过银行完成打款后，填写真实参考号登记，或填写原因拒绝申请。普通员工不能访问收款资料或审批申请。

订单详情可登记线下已经完成的全额退款；这不会调用支付平台退款。退款会回冲该订单的佣金，并拒绝该代理的所有待处理提现申请，让其核对新余额后重新申请。已打款记录不会被抹掉，因此可能出现负余额；负余额会由之后赚取的佣金抵扣。仅在商家确认商品已收回并选择恢复库存时恢复库存，重复登记不会重复增加库存。暂不支持部分退款。

此功能包含本地与 Supabase 两种实现。增量迁移是 `202611040002_finance.sql`；迁移会保留已存在的核心 RPC，将新增财务路由放在新的受控入口，旧核心 RPC 不再允许浏览器直接调用。现有数据库仍需先审查结构、备份并验证迁移。

## 验证邮件跳到 localhost 的修复

注册、团队邀请及重发验证邮件都会显式提交 `emailRedirectTo`，值为当前网站 origin 加 Vite 的应用 base 路径（包括 GitHub Pages 的仓库路径）。回跳不会包含当前订单或邀请查询凭证。登录界面提供「重新发送验证邮件」；新链接通过用户点击该按钮获取，不会自动给客户发送邮件。

Supabase 仍须允许该回跳网址。项目管理员需在 Authentication → URL Configuration 中设置实际 Site URL，并将同一应用根网址加入 Redirect URLs。匿名前端 key 无权修改 Auth 管理配置，应用不能绕过这项限制。旧邮件的链接不会随代码变更而更新。GitHub Pages 发布工作流是手动的，代码 push 后需发布新构建才会更新线上界面。

CI 额外构建隔离的邮件验证页面，所有远端请求均被测试拦截，无需真实 Supabase 项目，也不会发送邮件。手动验证可执行：

```sh
VITE_SUPABASE_URL=https://auth-test.supabase.co VITE_SUPABASE_ANON_KEY=browser-test-public-key npm run build -- --outDir=auth-test-dist
EZSHOP_AUTH_TEST_DIST=auth-test-dist python tests/auth_browser.py
```

## 商家图片上传

店铺 Logo、Banner 和商品图片改为直接选择文件、自动上传并预览，不要求商家手填图片网址。JPG、PNG、WebP 最大 5 MB；前端检查图片能否解码及像素数量；上传失败不会替换已有图片。图片成功上传后仍须保存店铺资料/商品，才会应用到顾客端。移除图片只清除当前引用，不删除仍可能被其他位置引用的文件。

- 本地模式：图片保存在 `EZSHOP_DB` 所在目录的 media 子目录，通过受限的公开图片路径提供；上传要求有效商家/经理/库存专员身份。目录随业务数据库保留，不上传 GitHub。
- Supabase：新增迁移 `202611040003_media.sql`，建立公开的 `ezshop-media` bucket、5 MB/MIME 限制和对象策略。**已运行 001/002 的项目仅运行新增 003，不要重跑旧迁移。** bucket 只用于公开的店铺/商品图片，不用于顾客付款凭证或私密文件。每个上传者只能写入自己 UUID 目录，不授予覆盖和删除权限；代理、订单客服及匿名用户不能上传。
- 已存在同名 bucket 但配置不匹配时迁移会停止，避免擅自改变已有文件的公开范围。
- 本地 PostgreSQL 测试模拟 Storage 表与策略，不能代替实际 Supabase Storage 服务验证。003 尚需项目管理员在真实项目执行；anon Key 无权初始化存储。

店铺设置也说明了实际经营流程：商家添加商品后，把 EZShop 店铺链接分享到直播/社交渠道，顾客通过该链接下单。当前没有 TikTok Shop/Facebook 平台内订单自动同步，也没有把社交主页链接当作订单接口。

## 邮费与寄件（商家自行安排）

商家在店铺设置填写每单固定邮费（MYR，0 代表免邮）及常用快递公司。公司可以从建议列表选择，也可以自行输入；当前没有快递报价、叫件或面单 API。顾客填写姓名、Email、手机、街道地址、城市、5 位邮编和马来西亚州属。后端按当前商品金额加商家邮费生成订单，忽略客户端提交的金额；邮费不计入代理佣金。

订单保留当时的商品小计和邮费，之后改价不影响历史订单，相同结账请求重试也不会重算新邮费。商家自行寄出包裹后，可在已付款订单中记录实际快递公司及运单号；顾客凭原有订单访问凭证查看发货记录。重复登记同一运单不会重复写入，已登记的运单不能静默覆盖。

新增迁移 `202611040004_delivery.sql`，已有 001/002 的项目依次应用新增 003（图片存储）及 004（配送），不重跑旧迁移。当前只支持每单固定邮费和马来西亚配送；按重量、分区、多包裹、到付、自动物流追踪及数字商品免地址流程尚未实现。

若本机已配置真实 Supabase，业务浏览器测试应使用独立的本地构建：

```sh
VITE_SUPABASE_URL= VITE_SUPABASE_ANON_KEY= npm run build -- --outDir=local-test-dist
EZSHOP_DIST=/workspace/multi-tenant-ecommerce/local-test-dist python tests/browser.py
```

业务浏览器测试会拦截所有非本机请求，避免误用真实项目创建测试商家或发送验证邮件。不要将 `local-test-dist` 用于正式网站发布。

## 品牌字体与账号找回

EZShop 英文品牌字使用自托管的开源 Racing Sans One 赛车风格字体，参考用户提供的粗斜字样，未声称识别出原图的确切字体。中文菜单保留易读的系统字体。字体许可随网站发布在 `public/licenses/`。

云端登录页提供「忘记密码」，重设邮件使用当前应用根地址回跳，沿用已有 Supabase Redirect URLs 配置。有效恢复会话才允许更新密码；密码更新成功后请求退出全部会话。如果退出失败，会明确提示密码已更新，避免误报为密码修改失败。账号不存在时使用统一请求提示，不通过页面泄漏账号是否注册。邮件的真实投递与密码策略仍由 Supabase Auth 配置决定，测试不会操作真实账号或发送实际邮件。

## 收款、订阅与维护

新增 `202611040005_payments.sql`、`payments` 和 `stripe-webhook` Edge Functions；商品收款与平台订阅使用独立账户和账本。前端新增「收款与订阅」及顾客安全付款入口；未配置的环境继续手动收款。回调核对签名、账号、币种及后端金额，重复事件幂等，异常进入核查。真实全额退款同步佣金回冲，部分退款与争议需要核查；没有自动退款或代理银行打款。

部署步骤、服务端密钥名称、测试模式验收及功能边界见 [上线配置](docs/上线配置.md)。源码提交不会自动部署。不要把支付密钥放在 GitHub Pages 的前端变量中。

本地 SQLite 备份使用 `python server/backup.py backup 源文件 --to 新备份文件`，恢复使用 `restore 备份文件 --to 新恢复文件`，验证使用 `verify 文件`。工具不覆盖已有文件；图片目录另行备份。它不操作 Supabase，生产备份仍需项目管理员配置与恢复演练。

## 多语言界面

顾客端及商家端（含登录、账号找回、代理和员工功能）支持中文、English、Bahasa Melayu、ไทย、ខ្មែរ、Tiếng Việt。平台管理页仅提供中文和英文。页面上方可切换语言，首次进入顾客端和商家端参考浏览器的语言偏好；手动选择后优先使用已保存的选择。三个端的选择分别保存在当前浏览器，刷新后保留，平台仍仅中英。浏览器语言只是语言建议，不代表已识别国籍或所在地；浏览器没有支持的语言时默认英文。界面翻译本身不需要迁移；商品多语言内容使用下述新增 007 迁移。

商品名称、介绍、规格、分类、店铺名称与简介支持六语版本，顾客切换后优先读取对应版本，空白回退原文；原始字段仍保留。商家在商品/店铺表单维护译文，无需外部翻译服务。顾客姓名、电话、地址及备注不自动改写；表单标签随语言切换。订单保存成交时的商品多语言快照与顾客所选语言，后续改商品不影响历史订单。邮件及服务商托管页面仍由各自配置决定。结算仍是 MYR，配送范围仍是马来西亚。

界面词库为 `src/locales/messages.json`，每个中文原文对应 `[en, ms, th, km, vi]` 五个译文；`src/i18n-core.ts` 定义语言范围和参数插值。新增文案应通过 `useI18n().t` 引用，避免对来自数据库的名称调用翻译。泰文及高棉文字体自托管，许可保存在 `public/licenses/`，不会调用在线翻译服务。

`npm run test:i18n` 检查词库完整性、页面硬编码文字及占位参数。`tests/i18n_browser.py` 用隔离的本地数据库验证六语切换、平台双语限制、跨语言下单、原文保留及手机布局，不访问真实 Supabase 或支付服务。

## 商品及店铺多语言内容配置

新增 `supabase/migrations/202611050007_content_languages.sql`，保留已有原文字段，增加六语 JSONB 内容、订单快照及翻译用量记录。已完成 001–006 的项目只应用新增 007；缺少 005/006 时先按顺序补齐缺少的迁移，不重复已执行的迁移。007 会检查依赖。远端未执行迁移时，界面显示多语言内容未启用，不会让商家误以为译文已保存。

商品及店铺内容仅由商家手动维护各语言版本，不配置或调用自动翻译服务。旧 `translate-content` 函数升级后返回 410，避免旧客户端继续调用外部翻译服务；历史数据库字段保留以兼容已有内容。

本地 Python/SQLite 开发模式同样仅支持人工维护和浏览；没有自动生成入口，旧接口返回 410。`tests/content_browser.py` 验证浏览器默认语言、手动选择优先、六语商品、购物车、下单及订单快照。纯函数测试使用模拟服务结果，未调用真实翻译服务。
