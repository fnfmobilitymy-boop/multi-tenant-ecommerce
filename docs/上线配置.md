# EZShop 上线配置与验收

本文区分源码功能和实际服务启用。提交源码不会自动发布正式网站。真实支付账户、订阅价格、认证邮件、远端备份和正式环境验证需要项目拥有者的相应权限；当前环境只有前端公开 Supabase 配置。

## 六个阶段的交付范围

| 阶段 | 已有源码功能 | 上线前仍需验证或配置 |
| --- | --- | --- |
| 顾客商店 | 独立 slug、分类搜索、商品详情、购物车、地址、服务器计价、固定邮费、安全订单查询 | 实际商家的商品和库存；每商品填写一个实际规格并保存订单快照；不同规格分别建商品管理，不支持规格组合；折扣、数字商品免地址流程未开放 |
| 收款与通知 | 手动确认实际收款；Stripe Connect 托管支付、验签和金额核对；收据与提醒任务；全额退款同步与佣金回冲 | 部署新增数据库/函数、商家身份认证、测试交易、邮件域名与定时任务；未接 CHIP、Billplz、独立 DuitNow QR |
| 代理佣金 | 代理链接、业绩、独立权限、提现申请、人工转账登记、退款回冲 | 核实实际佣金政策和银行打款；系统不会自动银行转账 |
| 平台与订阅 | 管理商家、暂停店铺、手动方案分配；Stripe 独立订阅 Checkout、账单管理、真实账单回调 | 配置真实 Pro 价格、平台收款账户、Billing Portal；平台管理员须由可信数据库管理操作授权 |
| 商家团队 | 经理、库存、订单客服、代理邀请与撤销；商家和角色隔离；操作记录 | 实际团队邮箱验证与权限验收 |
| 发布与维护 | CI、手动 Pages 发布、数据库和浏览器测试、本地备份/恢复工具 | Supabase 生产备份恢复演练、监控、容量与并发验证、真实服务端到端验收 |

## 仅新增支付迁移

已经应用 001–004 的项目，只审查并依次应用新增 `supabase/migrations/202611040005_payments.sql`、`supabase/migrations/202611040006_product_specs.sql` 及 `supabase/migrations/202611050007_content_languages.sql`。已经完成 005/006 时只应用新增 007。不要重新运行旧迁移，也不要删除已有业务表。005 新建独立的支付 RPC 和私有支付记录，不替换已有商家后台接口。迁移须先在测试项目验证、备份，再应用到正式项目；当前未自动远程执行。

## 支付服务的服务端配置

Supabase Edge Functions 的安全配置中设置以下名称，值仅保存在服务端：

| 名称 | 用途 |
| --- | --- |
| `APP_URL` | 实际应用根网址，必须以 `/` 结束，包含仓库路径，例如 `https://fnfmobilitymy-boop.github.io/multi-tenant-ecommerce/` |
| `STRIPE_SECRET_KEY` | 平台 Stripe 服务端 key，先使用测试模式；不放入 GitHub Pages 或任何 `VITE_` 变量 |
| `STRIPE_PRO_PRICE_ID` | 平台自行创建的 MYR 周期订阅价格 ID；最终价格和条款在 Stripe 页面展示 |
| `STRIPE_WEBHOOK_SECRET` | 平台订阅 webhook 的签名密钥 |
| `STRIPE_CONNECT_WEBHOOK_SECRET` | connected accounts 事件 webhook 的签名密钥 |

Supabase 自带的 URL、anon key 和 service role key 由 Edge 服务端使用；不把 service role key 放入前端。先在测试项目审查部署 `payments` 与 `stripe-webhook`。项目 `supabase/config.toml` 中这两个函数的网关 JWT 检查关闭：`payments` 自行验证商家 bearer token，顾客付款要求订单独立访问凭证；`stripe-webhook` 必须通过 Stripe 原始请求签名验证，普通匿名请求无法伪造成功。

Webhook 地址为该项目 `/functions/v1/stripe-webhook`，Stripe 中分别创建平台事件和 connected accounts 事件目标并保存各自的签名密钥。订阅至少启用 `checkout.session.completed`、`checkout.session.expired`、`invoice.paid`、`invoice.payment_failed`、`customer.subscription.updated`、`customer.subscription.deleted`；商家收款至少启用 `account.updated`、`checkout.session.completed`、`checkout.session.async_payment_succeeded`、`checkout.session.async_payment_failed`、`checkout.session.expired`、`charge.refunded`、`charge.dispute.created`。使用与密钥一致的测试/正式模式。

在 Stripe 配置平台 Connect 和 Billing Portal。商家在「收款与订阅」完成服务商的账户认证，检查收款状态。商品款通过该商家的 connected account 收取，平台订阅款进入平台账户。卡或 FPX 的实际可用性取决于服务商对平台、地区及商家账户的批准；代码不代表已获批准，也不保证已开通 FPX。

## 付款异常与退款

只有已验签、匹配商家账户且金额/币种一致的已付款事件才会把订单更新为已付款。返回页面、Checkout 创建成功、订阅 session 完成均不能单独证明款项到账。事件重复不会重复确认或重复发送收据。订单取消后收到付款、金额不匹配、部分退款和支付争议进入核查记录。

当前后台退款按钮用于登记已经在外部完成的全额退款，不会调用银行或 Stripe 退款 API。服务商已完成的全额退款回调会自动回冲订单佣金并拒绝相关代理的待处理提现，不自动恢复商品库存。部分退款和争议须人工核对，不提供部分退款佣金分摊或自动争议处理。核查记录的「保存」只记录实际处理结果，不会转账、退款或自动改成已付款。

## 测试模式验收顺序

1. 在测试项目完成 005 和函数配置，确认未配置时页面明确提示，不发生扣款。
2. 两个商家分别绑定测试账户；确认商品款归对应商家，不能访问另一商家的订单及账单。
3. 下单后测试成功、取消、异步付款、重复 webhook、Webhook 暂时失败重试。
4. 同时测试人工取消/确认与线上支付冲突，核查记录须保留，库存不能重复增加。
5. 测试全额退款、部分退款核查、佣金回冲、已打款后的负余额。
6. 测试订阅未付款、成功、续费失败、取消和取消后重新订阅；只有实际有效账期和已付账单或真实试用才启用 Pro。
7. 配置 Resend 与通知任务，向受控测试邮箱验收收据和提醒；检查实际投递结果。
8. 完成生产备份及恢复演练，再由拥有者决定正式部署与支付模式切换。

## 备份与恢复

Supabase 的备份及 PITR 能力取决于项目方案，须在 Supabase Dashboard 的数据库备份功能确认实际可用性、保留周期及恢复方法。公开 anon key 无权创建或恢复生产备份。数据库备份通常不等于 Storage 图片文件备份，须另行安排图片备份并验证。

本地 Python/SQLite 开发模式可以使用：

```sh
python server/backup.py backup server/data/ezshop.db --to /安全目录/ezshop-backup.db
python server/backup.py verify /安全目录/ezshop-backup.db
python server/backup.py restore /安全目录/ezshop-backup.db --to /安全目录/ezshop-restored.db
```

工具使用 SQLite 在线一致性备份 API，检查数据库完整性与关联，只允许写入新文件，拒绝覆盖现有数据库。恢复不会替换正在运行的服务；先停止本地服务，再以 `EZSHOP_DB` 指向验证后的恢复文件。`media/` 图片目录另外备份。备份含顾客个人资料，不提交 GitHub、不放公开网页或 Actions artifact。此工具不会备份 Supabase。

## 手动发布

源码通过 CI 后，使用仓库 Actions 的 EZShop Pages 发布工作流，按现有要求输入 `DEPLOY`。前端构建只需要公开 `VITE_SUPABASE_URL`、`VITE_SUPABASE_ANON_KEY`。前端发布不会部署 SQL、Edge Functions、邮件任务或 Stripe 配置；这些服务须按上面步骤单独验收。Supabase Auth 的 Site URL 与 Redirect URLs 也必须指向实际应用根网址。

## 商品内容随语言切换

007 为商店和商品增加多语言内容，为订单商品保留成交时的语言快照。发布前先在测试项目验证增量迁移。未应用时页面明确提示未启用。原始内容始终保留，缺少译文回退原文；顾客的姓名、电话和地址保持原文。

自动翻译功能已按用户要求移除，不需要 Google 翻译 API。商家可以手动填写各语言内容，未填写时回退原文。更新后端函数会将旧 translate-content 入口替换为停用响应。

## Stripe 开放开关

Stripe 自动付款入口默认关闭，商家端显示人工核款及平台订阅申请。测试模式下配置服务端密钥、Connect 和 Webhook 并完成验证后，才将 Repository Variable `VITE_STRIPE_AUTOMATION_ENABLED` 设为 `true` 并重新发布前端。前端开关只控制入口，不是后端权限控制或付款证明；付款状态仍由后端验签处理。Secret `STRIPE_SECRET_KEY` 不得写入此变量或任何 `VITE_` 变量。平台 Stripe 自填金额链接仍是独立的人工核款方式，不依赖此开关。

## Pro 月费与税率

已确认 Pro 月费 MYR 99.90，另加 6% 税，每期 MYR 105.89（税额按 Stripe 账单舍入为 MYR 5.99）。在 Stripe 测试模式创建 MYR 99.90、每月一次的 recurring Price，将 price_ 编号保存为 Secret `STRIPE_PRO_PRICE_ID`；创建启用、6%、不包含在价格内的税率，将 txr_ 编号保存为 Secret `STRIPE_PRO_TAX_RATE_ID`。税种名称及登记信息按公司的真实情况填写。代码核验价格币种、金额、月周期及外加税率，未配置或不符时不创建付款会话；使用 Stripe tax_rates 生成账单税额，不能由前端传入金额。Stripe 手续费与该税额分开。

Free 为七天 Pro 试用，不设置另一套永久免费经营额度。试用到期后必须有有效续费授权才能经营。

## 七天试用与到期限制

010 增量迁移为新商家建立固定七天试用截止；已有商家从应用迁移时获得七天过渡期，重复升级不会重新延长。默认无需绑卡，试用内可选择绑定 Stripe：Checkout 沿用原截止时间，明确收集付款方式，试用结束后按月收费；未绑卡的商家到期需自行付款。取消或重新开户 Checkout 不重置试用。

主 RPC 在到期后返回续费所需的最小 Dashboard、拒绝业务操作和新顾客结账；Storage 上传也受限制。前端只显示续费及退出入口，团队成员提示联系所有者。已有订单的凭证查询及真实支付回调继续可用，避免丢失已成交订单。店铺公开页提示暂停接单。实际已付 Stripe 订阅或有效人工授权可恢复使用；付款失败且不在原七天试用内则停止经营。平台管理员不受商家套餐限制。

必须先应用 010 再开放试用/自动付款。Supabase 版本提供正式后端校验；本地 Python 模式用于隔离开发测试，不连接真实 Stripe 账单。

## 商家 Connect 开通失败排查

平台 Pro 订阅可用不代表 Connect 已获准创建商家账户。在相同 Stripe 测试/正式模式的 Workbench 请求日志查找失败的 POST /v1/accounts 或 /v1/account_links，仅查看 error.message；不得分享 Authorization、API key 或完整客户资料。服务代码只记录经过校验的 Stripe request_id、操作名及分类编号，不输出原始错误或请求内容。已知未启用 Connect、平台设置不完整、国家不受支持会显示具体提示，未知错误保留通用失败提示。收款卡片错误不会覆盖有效的订阅状态。

当前创建商家 Connect 账户使用 MY 国家和 Express 类型；平台须具备相应支持。多国商户的收款注册范围不能由六语界面或 MYR 结算推断，需逐国验证并扩展注册国家设置。此诊断更新不自动创建账户、开启 Stripe 平台权限或确认已可收款。
